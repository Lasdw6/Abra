Prepare the source

The driver uploads an Abra binary built for the source CPU, then runs it through the provider API or SSH. Save the application checkpoint before copying its files.

Why choose outside coordination?

Use this when you can run commands and copy files through an API or SSH. Your outside service manages capture and transfer. Only the temporary collector and runtime tools need to run inside.

What makes this portable?

A saved database or session file may work on another CPU. A compiled executable may need rebuilding. The destination must supply the right runtime and dependencies.

What each capture saves

A process list tells us what was running. It cannot restart a process at the same instruction. That needs a memory checkpoint, or application code that loads saved progress.

Proposed Daytona integration

Let Daytona capture the VM.

The proposed integration checks that the sandbox is a Linux VM, then requests includeMemory: true. After Daytona finishes, Abra records the snapshot ID and the account and region needed to use it.

We found no documented API for downloading the raw memory. Daytona keeps it. To restore, the receiver needs access to that provider snapshot, and the snapshot must still exist.

Stop changes before copying state.

A barrier ID labels the observation used by a file capture. It does not pause the application. Save an application checkpoint or stop every process that writes to the captured files. CRIU stops its selected process tree, but other writers can still change the workspace. If Abra collects files separately from a provider snapshot, they may describe different moments.

Who does what

The coordinator starts the capture, chooses the tools and tells the destination what to restore. It can run inside or outside.

The collector runs inside the source environment. It reads files and process information. It does not save arbitrary process memory.

An access driver runs commands and moves files. SSH is an access method. It does not provide a VM snapshot API.

A browser adapter can run inside Daytona.

The Daytona integration runs a command inside the sandbox. That command starts the browser adapter, which uses the browser debugging protocol to export session data. Abra captures and transfers the export alongside the workspace.

The proposed Daytona integration could also request a VM memory snapshot. The browser export would still provide application data for a destination that cannot use that native snapshot.
